# Dolphin CREATE 施設別ログイン 本番設計

2026-10-05 作成

本番では、施設ごとのID・パスワードを認証サービスで管理し、Dolphin CREATE のサーバーがログインした人の施設のデータだけを返します。試作版のログイン画面はこの設計の操作の流れを示したもので、保護の仕組みはこの設計で本番に入れます。

## 全体構成

ログインからデータ表示まで、施設の確認をサーバーとデータベースの2回行います。

1. **ブラウザ**：ログイン画面でID・パスワード（＋多要素認証）を入力。
2. **認証サービス**：本人確認をして、有効期限つきの証明書（トークン）を発行。パスワードはここだけで保管。
3. **Dolphin CREATE サーバー**：トークンから本人を特定し、「見られる施設」と権限を確認。対象外の施設は存在しないとして返す。
4. **データベース**：行ごとの制限で、その人の施設の行だけを返す。
5. **外部連携**：Google広告・Meta・GA4・Dolphin の取り込みは、施設ごとの接続情報でサーバーが実行し、ブラウザには接続情報を渡さない。

## アカウントと権限

アカウントは「施設コード」に属し、権限と見られる施設を持ちます。会場担当は自施設だけに固定し、本部のアカウントだけが複数施設を見られます。

| 権限 | 所属 | 見られる施設 | 承認できること | アカウント管理 |
| --- | --- | --- | --- | --- |
| 本部管理者 | 本部（HQ） | 全施設 | なし | 発行・変更・停止・再発行・ロック解除 |
| マーケ・データ（Aさん） | 本部（HQ） | 担当する施設 | データ・計測の承認 | なし |
| 制作・ブランド（Bさん） | 本部（HQ） | 担当する施設 | 表現・ブランドの承認、素材の権利確認 | なし |
| 施設管理者 | 各施設 | 自施設のみ | 事実・素材・予算の承認、月間予算上限の設定 | 自施設の担当者の発行・停止 |
| 会場担当 | 各施設 | 自施設のみ | 事実・素材・予算の承認 | なし |
| 閲覧のみ | 各施設 | 自施設のみ | なし | なし |

試作版にない「施設管理者」と「閲覧のみ」は、施設側で担当者の入れ替えを本部に頼まずに行えるよう本番で加える案です。1人が複数の権限を持つ場合は、承認の欄で同じ人が2つ以上承認できないようにします。

## ログインとパスワードの決まり

ログインIDはメールアドレスを推奨します。パスワード再設定を本人に届けられ、施設コードを覚える必要もなくなるためです。

| 項目 | 本番の設定案 | 試作版 |
| --- | --- | --- |
| ログインID | メールアドレス（施設コードはアカウントに紐付けて自動判定） | 施設コード＋ログインID |
| パスワードの長さ | 12文字以上。漏えい済みパスワードの一覧と照合して弾く | 10文字以上・英字と数字 |
| パスワードの保管 | 認証サービスが専用の方式（bcrypt・Argon2など）で保管。Dolphin CREATE には持たない | ページ内に保持（保護なし） |
| 初回ログイン | 招待メールのリンクから本人が設定。仮パスワードを人が伝えない | 仮パスワード→初回変更 |
| 多要素認証 | 本部管理者・施設管理者は必須。他は推奨（認証アプリ） | なし |
| ロック | 5回続けて失敗で15分ロック。繰り返すと管理者が解除 | 5回でロック・管理者が解除 |
| 自動ログアウト | 無操作30分、ログインから最長12時間 | 無操作30分 |
| エラー表示 | どの項目が違うかを出さない | 同じ |
| パスワード再設定 | 本人がメールで再設定。管理者は再設定メールの送信のみ | 管理者が仮パスワードを再発行 |
| ログイン履歴 | 成功・失敗・ロック・権限変更を1年保存 | 画面でのみ表示 |

社内で Google Workspace や Microsoft 365 を使っている場合は、本部のアカウントだけそのアカウントでログイン（シングルサインオン）することもできます。

## 施設ごとのデータ分離

画面で施設を隠すだけでは分離になりません。サーバーとデータベースの2か所で、他施設のデータを返さないようにします。

- **全テーブルに facility_id**：接客データ・広告実績・クリエイティブ・画像・承認履歴のすべてに施設IDを持たせる（仕様書の「テーブル」に追加）。
- **サーバーでの確認**：すべての読み書きで、ログインした人の「見られる施設」にその施設IDが含まれるかを確かめる。含まれなければ、存在しないとして返す。
- **データベースでの制限**：行ごとのアクセス制限（PostgreSQL の行レベルセキュリティなど）をかけ、サーバーの書き忘れがあっても他施設の行が読めないようにする。
- **画像とファイル**：施設ごとの保管場所に分け、時間制限つきの署名URLでだけ表示する。
- **広告・Dolphin の接続情報**：Google広告・Meta・GA4・Dolphin の認証情報は施設ごとに暗号化して保管し、画面には出さない。
- **AIへの入力**：1回の依頼に含めるのは1施設の匿名集計だけ。施設をまたいだ比較は本部の権限でのみ行う。
- **操作の記録**：承認・入稿・書き出し・アカウント変更を、誰が・いつ・どの施設で行ったか記録する。

## 構築手順

認証サービスの選定から始め、データ分離を入れてから実データを入れます。分離を後から足すと、既存データの移し替えが必要になるためです。

1. **認証サービスを選ぶ**：候補は Firebase Authentication（Google Cloud Identity Platform）、Auth0、Supabase Auth、Microsoft Entra External ID。施設ごとの分離（マルチテナント）、多要素認証、パスワード条件の設定、料金、社内の既存環境との相性で比べる。
2. **施設とアカウントのテーブルを作る**：`facility`、`app_user`（認証サービスのユーザーIDと紐付け）、`user_facility_role`（誰がどの施設で何の権限か）、`auth_audit`。
3. **全テーブルに facility_id と行ごとの制限を入れる**：権限のない施設の行が読めないことを、テスト用の2施設で確かめる。
4. **ログイン画面と招待の流れを作る**：招待メール→本人がパスワード設定→多要素認証の登録。試作版の画面をそのまま元にする。
5. **アカウント管理画面を作る**：発行・権限変更・停止・ロック解除・履歴。本部管理者と施設管理者で操作できる範囲を分ける。
6. **広告・Dolphin の接続情報を施設ごとに登録する**：暗号化して保管し、取り込み処理は施設ごとに動かす。
7. **受入テストを行う**：次の節の項目をすべて通す。
8. **1施設で本番を始める**：仕様書の第1段階と同じく1施設から始め、問題がなければ施設を増やす。

## 受入テスト

公開前に、テスト用の2施設と各権限のアカウントで次をすべて確かめます。**この10項目がすべて通ることを M1 の完了条件とします。**

- [ ] 会場Aの担当者が、会場BのURLやデータIDを直接指定しても、会場Bのデータが返らない
- [ ] 会場Aの担当者のCSV・Excel書き出しに、会場Bの行が1行も含まれない
- [ ] 会場Aの担当者が会場Bの画像の署名URLを開いても表示されない
- [ ] ログアウト後や自動ログアウト後に、ブラウザの「戻る」でデータが見えない
- [ ] 5回失敗でロックされ、ロック中は正しいパスワードでも入れない
- [ ] 停止したアカウントは、ログイン中でも次の操作から使えなくなる
- [ ] 権限を変えると、承認ボタンの表示とサーバー側の承認可否が両方変わる
- [ ] 本部管理者と施設管理者は、多要素認証なしでは入れない
- [ ] ログインの成功・失敗・ロック・権限変更が履歴に残る
- [ ] AIへの依頼に他施設のデータや個人情報が含まれない（送信内容を記録して確認）

## 運用

アカウントは「依頼→発行→定期点検→削除」の流れで管理します。

- **発行**：施設管理者または本部が、氏名・メール・権限を入力して招待。共用アカウントは作らず、1人1アカウントにする。
- **異動・退職**：当日中に停止。承認履歴に名前が残るため、削除ではなく停止にする。
- **定期点検**：四半期ごとに、各施設のアカウント一覧と権限を施設管理者が確認する。90日使われていないアカウントは停止候補にする。
- **問い合わせ**：ロック解除やパスワードの相談は施設管理者、施設管理者自身の分は本部が受ける。

## 決めていただきたいこと

- [ ] 認証サービスとホスティング先（社内で使っているクラウドがあればそれに合わせる）
- [ ] ログインIDをメールアドレスにするか、試作版と同じ「施設コード＋ID」にするか
- [ ] 施設側のアカウント発行を「施設管理者」に任せるか、本部だけが行うか
- [ ] 多要素認証を全員必須にするか、管理者だけにするか
- [ ] 本部のアカウントを Google Workspace・Microsoft 365 のシングルサインオンにするか
- [ ] 最初に本番を始める1施設と、その施設管理者
